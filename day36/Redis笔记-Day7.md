# Day 36 · W6 Redis Day 7：过期策略 + 分布式锁（W6 收官战）

> 2026-09-07（一）· 面试高频考点：过期删除双策略 / 内存淘汰 LRU / SET NX EX 分布式锁 / 释放锁 Lua 脚本

## 1. 过期删除策略：惰性 + 定期

key 设了过期时间（EXPIRE），靠什么清掉？

| 策略 | 原理 | 类比 |
|---|---|---|
| **惰性删除** | 等你 GET 这个 key 时才检查，过期了就顺手删 | 懒人式：用到才清理 |
| **定期删除** | Redis 每隔一段时间主动抽查一批过期 key 删掉 | 保洁式：定时巡逻 |

**两者配合**：惰性兜底（每个 key 访问时都被查）+ 定期主动清（防止过期 key 一直占内存）。

## 2. 内存淘汰策略（内存满了怎么办）

配置 `maxmemory-policy`，常见三种：

| 策略 | 行为 | 适用 |
|---|---|---|
| `noeviction` | 满了直接报错（默认） | 绝不能丢数据的场景 |
| `allkeys-lru` | 删**所有 key 中**最近最少用的 | 纯缓存，都可丢 |
| `volatile-lru` | 只在**设了过期时间**的 key 里删最近最少用的 | 混合场景 |

> **LRU = Least Recently Used 最近最少使用**（面试必问缩写含义）
> 记忆：哪本书最久没翻开就先收哪本。

## 3. 为什么需要分布式锁

Java 的 `synchronized` 只锁**单台机器**（一个 JVM 内）。生产是多台服务器部署，A 机器和 B 机器各自有自己的锁 → 管不住彼此 → 需要"**大家都看得见的锁**" = Redis。

> 场景：多台服务器同时扣库存，单机锁失效 → Redis 分布式锁。

## 4. 加锁：SET ... NX EX（一条命令原子完成）

```bash
SET lock:order NX EX 30
# NX = Not eXists，键不存在才成功（抢锁）
# EX 30 = 30 秒自动过期（防死锁）
```

- 抢到 → OK；没抢到 → (nil)（别人持有中）
- **为什么必须一条命令**：早期错误写法是 `SETNX` 加锁 + 再单独 `EXPIRE` 设过期——**两步不原子**，万一第一步成功、第二步执行前机器挂了 → 锁永不过期 = 死锁！
- **为什么带 EX**：持锁的机器突然宕机，30 秒后锁自动释放，别人能继续抢——不会死锁

> 口诀：**加锁必须带过期，NX EX 一条命令。**（呼应 INCR 铁律：能用一条命令原子完成，绝不拆两步）

## 5. 释放锁：先验明正身，再删除（Lua 脚本原子）

**问题**：A 的锁 30 秒过期后，B 抢到了锁；此时 A 业务干完来释放，如果直接 `DEL` → 把 **B 的锁删了** → C 又能抢到 → A/B/C 同时持锁 = 锁形同虚设。

**解决**：锁的值存一个**唯一标识**（如 uuid），释放前先比对"是不是我的锁"，是才删。比对 + 删除必须原子 → 用 **Lua 脚本**（Redis 保证脚本内多条命令原子执行）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

> 真实工作：直接用 Redisson 框架（自带看门狗自动续期），但面试要能说出上面这层原理。

## 6. 实测记录（myredis 容器）

```bash
docker exec -it myredis redis-cli --raw

SET lock:order NX EX 30   # → OK（服务器 A 抢到锁）
SET lock:order NX EX 30   # → (nil)（服务器 B 抢失败，A 还持着）
GET lock:order            # → 唯一标识（生产是 uuid）
DEL lock:order            # → 1（业务完成，手动释放）

CONFIG GET maxmemory-policy   # → 看当前淘汰策略（默认 noeviction）
```
