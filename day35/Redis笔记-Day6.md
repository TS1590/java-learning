# Day 35 · W6 Redis Day 6：持久化 RDB / AOF

> 2026-09-07（一）· Redis 重启后数据为什么还在？—— 内存断电就丢，必须落盘

## 1. 为什么要持久化

Redis 数据在**内存**里 → 断电/宕机 = 数据全没 → 必须定期把数据写到**磁盘**。

两种方式：**RDB（快照）** 和 **AOF（追加日志）**。

## 2. RDB：快照（拍照片存档）

**原理**：把内存数据**整个拍张照**存进磁盘文件（dump.rdb），像游戏"存档"。

**触发方式**：
```bash
SAVE         # 手动同步存档（会阻塞，数据量大时卡）
BGSAVE       # 后台存，不卡（工作中用这个）
# 自动：按规则触发，如 60 秒内改了 1 万次 → save 3600 1 300 100 60 10000
```

**优点**：文件小、恢复快、适合做备份
**缺点**：**可能丢数据**——两次快照之间的修改会丢

## 3. AOF：追加日志（录像重放）

**原理**：每一条**写命令**都记进日志文件（appendonly.aof），重启时把命令**重放一遍**还原数据。

**开启与刷盘策略**：
```bash
CONFIG GET appendonly    # 默认 no（默认没开！）
appendonly yes           # 配置文件里开启
# fsync 刷盘三档：
#   always   每条命令都刷盘 —— 最安全、最慢
#   everysec 每秒刷一次 —— 默认，最多丢 1 秒（推荐）
#   no       交给操作系统 —— 最快、最不安全
```

**优点**：**丢数据少**（最多丢 1 秒）
**缺点**：文件大、恢复慢

## 4. 核心区别（一句话答题版）

> **RDB = 存"结果快照"**（定期把整份数据存下来，可能丢两次快照之间的数据）
> **AOF = 存"过程日志"**（每条写命令都记录，重启重放，最多丢 1 秒）

| 对比 | RDB | AOF |
|---|---|---|
| 存什么 | 数据快照（结果） | 写命令（过程） |
| 数据丢失 | 两次快照之间全丢 | everysec 最多丢 1 秒 |
| 文件大小 | 小 | 大 |
| 恢复速度 | 快 | 慢 |
| 典型用途 | 备份、快速恢复 | 保数据不丢 |

## 5. 真实工作怎么配：两个都开

**RDB 做快速备份恢复 + AOF 保数据不丢。**

> 经典事故：只开 RDB，Redis 宕机丢了半小时订单数据 → 被投诉。
> 所以线上默认 AOF 也开（everysec，最多丢 1 秒可接受）。

## 6. 实测记录（myredis 容器）

```bash
docker exec -it myredis redis-cli --raw
CONFIG GET save           # 看自动快照规则
CONFIG GET appendonly     # → no（AOF 默认没开）

SET name 持久化测试
SAVE                      # 手动触发一次快照
docker exec -it myredis ls -lh /data   # 看 dump.rdb 是否生成
docker restart myredis    # 重启容器
GET name                  # → 持久化测试 ✅ RDB 生效，数据还在
```
